Morkql
A MeTTa-Shaped Query Language for Mork Path Spaces
Draft Language and Compilation Specification, Version 0.1
Proposal for discussion and prototyping
July 12, 2026

Abstract
Morkql is a declarative, S-expression query language intended for end-user access to Mork
knowledge bases and for direct embedding in MeTTa. It presents familiar pattern queries, set
composition, and Datalog-style recursive rules while compiling without a new runtime layer to
the existing Morkl algebra of finite path spaces. The language is designed so that elaboration
can produce a checkable certificate relating a surface query, its logical plan, its physical path
plan, and the emitted Morkl program. This document specifies the proposed syntax, static
semantics, denotational semantics, lowering rules, verification profile, MeTTa API, and a lossless
low-level escape hatch called Morkql Core.

Status. This is a design proposal, not an official standard of the Mork, Morkl, Zippy,
MeTTa, or OpenCog Hyperon projects. The specification deliberately separates stable
semantic requirements from implementation-dependent details such as the current byte
encoding of MORK expressions and the exact serialized form of proof certificates.

1

Introduction

1.1

Purpose

5

Morkl provides a compact algebra for finite sets of structured paths. Its constructors are well
suited to formal reasoning and low-level optimization, but ordinary users usually think in terms
of facts, variables, conjunctions, derived relations, graph reachability, and named views. Morkql
bridges those levels.
A Morkql implementation accepts a quoted MeTTa-shaped query, checks it, chooses physical
path layouts, and immediately emits ordinary Morkl. The backend therefore need not implement a
separate query evaluator. Existing Morkl optimizers, trie executors, zipper executors, and proof
machinery remain the execution substrate.
The intended compilation chain is:
MeTTa atom containing MORKQL
|
v
parse and macro-expand
|
v
checked logical query IR
|
v
binding-mode and index planning
|
v
MORKQL Core / initial MORKL
|
v
optimized MORKL
|
v
trie, zipper, or operation-graph execution

1.2

Scope

This document specifies:
• a surface query language based on find, set operators, and Datalog-shaped rules;
• schema declarations that separate logical relations from physical path layouts and indexes;
• safety, typing, recursion, negation, and grounded-operation checks;
• a denotational semantics over finite sets of ground atoms and finite path spaces;
• lowering to Morkl, including the use of the multi-pattern-query macro MQT and unionsaturating fixed points;
• a one-to-one low-level syntax for Morkl constructors;
• a MeTTa-facing API and a proof-carrying compilation result; and
• conformance requirements and worked examples.
This document does not standardize transactions, persistence, distribution, a cost model, the
internal MORK byte encoding, or the complete MeTTa evaluator.

2

Background

2.1

MORK data and path tries

MORK stores expressions in a prefix-oriented representation backed by a radix trie. The current
MORK documentation describes S-expressions as sequences containing arity information, symbols,
new-variable markers, and variable references. It also emphasizes a practical consequence: queries
are most efficiently indexed when a large ground prefix precedes unbound material [5].
The concrete byte encoding is explicitly subject to change. Morkql therefore specifies an
abstract, injective encoding function from logical atoms to paths rather than freezing a particular
byte layout.

2.2

MORKL and Zippy

The Zippy formalization presents a space as a finite set of words over path items. The same value
can be interpreted as a relation, a tagged database, a trie, a finite language, or a graph encoding.
The core includes union, intersection, subtraction, path composition, prefix restriction, wrapping,
unwrapping, tails, first-symbol iteration, grounded operations, and recursion [2, 3].
The key structural operator is Morkl Iteration. It groups a path space by its first item, binds
the head item, binds the set of remaining tails, and evaluates a template for each group. In the
reference semantics, joins and projections can be implemented by composing iteration with prefix
operations. Recursive Datalog examples use union-saturating fixed points [2].
The formalization also supplies set, eager-trie, zipper, and operation-graph views, with proof
obligations connecting optimized programs to the reference path-set semantics [1, 4].

2.3

MeTTa as a host syntax

MeTTa represents programs and data using atoms and expressions, supports variables with a dollarsign spelling, and exposes atom spaces through grounded operations. The Hyperon implementation
and documentation make quoted atoms and custom spaces a natural place to host a query DSL
[7, 8].
Morkql uses MeTTa-shaped syntax but defines its own closed query AST. A quoted Morkql
expression is data for the Morkql compiler; it is not arbitrary MeTTa code to be reduced by the
general evaluator.

2.4

7

The usability gap

A low-level algebraic term exposes implementation-relevant structure but makes simple questions
verbose. For example, a user asking for mothers wants to state two facts sharing a variable:
(find (Mother $child $mother)
(child $child $mother)
(female $mother))

The corresponding Morkl plan may involve nested pattern unification, restriction, unwrapping,
intersection, iteration, and wrapping. Those operations should remain visible in an explain plan and
available in a core escape hatch, but they should not be mandatory surface syntax.

3

Goals, Non-Goals, and Design Decisions

3.1

Primary goals

1. Immediate lowering. Every accepted surface construct expands to ordinary Morkl before
execution. No new backend query operator is required.
2. MeTTa-shaped use. Queries are ordinary S-expressions that can be quoted, stored, generated,
transformed, and passed through MeTTa.
3. Declarative semantics. The meaning of a query is independent of join order, index choice,
and materialization strategy.
4. Trie-aware planning. The compiler may exploit grounded prefixes, alternate path layouts,
and virtual zipper views.
5. Verification support. Static checks and compilation steps expose small proof obligations and
explicit trust boundaries.
6. Lossless escape hatch. Advanced users can write every supported Morkl constructor through
Morkql Core.

3.2

Non-goals

Morkql is not intended to replace general MeTTa reduction, define a universal ontology, hide
all physical costs, guarantee termination of arbitrary grounded code, or standardize distributed
transactions. It also does not require SQL-like bags, nulls, implicit coercions, or global result
ordering.

3.3

Why find is the central form
Design rationale. A multi-pattern comprehension is the smallest friendly abstraction that
covers selection, projection, joins, and result construction. The existing Morkl examples already
define a multi-pattern-query helper, MQT, that recursively unifies a list of path patterns and
emits a template when the bindings are consistent. Giving that pattern a first-class surface
spelling adds ergonomics without adding a new semantic primitive.

3.4

Why Datalog-shaped rules are used for recursion
Design rationale. Users recognize reachability and derived relations more readily as rules than
as a hand-written recursive algebra term. Positive rule groups have a direct least-fixed- point
meaning, admit standard safety and stratification checks, and compile to Morkl Fixpoint plus
unions of MQT expansions.

MORKQL Draft Specification 0.1

3.5

8

Why queries are quoted data
Design rationale. Treating a query as a closed AST prevents accidental evaluation by unrelated
MeTTa rules, makes alpha-renaming and hashing deterministic, and gives the compiler a finite
language to type-check and certify. An implementation may register a non-eager grounded
operation that removes the need for explicit quote, but quoted syntax is the portable form.

3.6

Why set semantics are mandatory
Design rationale.
Morkl spaces are finite sets of paths. Making Morkql set-valued
preserves direct lowering, gives idempotent union, avoids duplicate-sensitive proof obligations,
and matches the semantics of graph reachability and Datalog consequence sets. Users who need
multiplicity must encode it explicitly as data.

3.7

Why logical relations are separated from physical layouts
Design rationale. In a prefix trie, argument order can dominate lookup cost. A logical
predicate such as parent(parent, child) should not change meaning merely because the engine
chooses a child-first index. Schema layouts allow the planner to select a grounded prefix while a
certificate records the index-coherence fact on which that choice depends.

3.8

Why pure queries and updates are separate
Design rationale. A pure query denotes a space. An update denotes a state transition.
Keeping the two forms distinct simplifies composition, caching, equivalence checking, and proofs.
All mutating API operations therefore carry an exclamation mark.

3.9

Why there is a core language
Design rationale. Not every path-space program is naturally relational. Prefix cylinders,
universal tail intersection, folds, and explicit virtual tries are valuable low-level tools. A lossless
core syntax prevents the friendly surface from becoming an expressive bottleneck and supplies a
readable target for compiler output.

4

Semantic Domains

4.1

Paths and spaces

Let Σ be the set of MORK path items. A path is a finite word over Σ:
Path = Σ∗ .
The empty path is ϵ. A path space is a finite set of paths:
Space = Pfin (Path).
Concatenation of paths is written p · q. Concatenation of spaces is language product:
A · B = {p · q | p ∈ A, q ∈ B}.

MORKQL Draft Specification 0.1

4.2

9

Logical atoms

A logical atom is a ground MeTTa atom accepted by the configured MORK codec. Let Atomg
denote the set of such ground atoms. Variables are not members of Atomg ; they occur only in
templates and patterns.
A MORK codec supplies partial inverse functions:
Enc : Atomg → Path,

Dec : Path ⇀ Atomg ,

with the required round-trip property:
Dec(Enc(a)) = a.
An implementation MAY use relation-specific layouts instead of the default codec. Each selected
layout must be injective over the relation’s well-typed ground facts.

4.3

Variables and substitutions

A variable token begins with $. A substitution θ ∈ Subst is a finite map from variables to ground
terms. Applying θ to a term, atom, pattern, or template is written θ(x).
The token $_ is anonymous. Each occurrence is alpha-renamed to a distinct fresh variable before
any other analysis.

4.4

Knowledge sources

A logical source D is a finite set of ground atoms. A physical source is a MORK space containing
one or more coherent layouts of those facts. Query semantics is defined over D; compilation and
execution operate over physical path spaces.

4.5

Pattern matching

For a pattern P and ground atom a, the relation
match(P, a) = θ
holds when first-order structural unification succeeds and returns substitution θ. Repeated
occurrences of a variable must receive the same ground term. Pattern matching does not execute
arbitrary MeTTa reduction.

5

Surface Syntax

5.1

Lexical conventions

MORKQL reuses the host MeTTa tokenizer. Symbols, strings, numbers, variables, and parenthesized
expressions are host atoms. A semicolon begins a line comment where the host parser permits
comments.
The following tokens are reserved in query position:
find query where yield union intersect except rules export
<- not test core

A relation may use one of those symbols only through an implementation-defined escaping
mechanism.

Abstract grammar

The following grammar is informative EBNF. The host parser first produces atoms; the MORKQL
parser then recognizes the forms below.
query

::= find-query
| long-query
| set-query
| rules-query
| core-query

find-query

::= "(" "find" template goal* ")"

long-query

::= "(" "query"
"(" "where" goal* ")"
"(" "yield" template ")"
")"

set-query

::= "(" "union" query query+ ")"
| "(" "intersect" query query+ ")"
| "(" "except" query query ")"

rules-query
rule-option
clause

::= "(" "rules" rule-option* clause+ ")"
::= "(" "export" relation-name+ ")"
::= "(" "<-" relation-pattern goal* ")"

core-query

::= "(" "core" core-space ")"

5.3

The find form

(find TEMPLATE GOAL-1 ... GOAL-N)

The form emits one instantiated copy of TEMPLATE for every consistent substitution satisfying all
goals. Results are deduplicated by set semantics.
The long form is exact sugar:
(query
(where GOAL-1 ... GOAL-N)
(yield TEMPLATE))

expands to:
(find TEMPLATE GOAL-1 ... GOAL-N)

MORKQL Draft Specification 0.1

5.4

11

Goals

A relation pattern is matched against facts in the current logical source.
(= A B) adds a unification constraint. It may bind an otherwise unbound variable when doing
so is unambiguous and type-correct.
(!= A B) succeeds when both sides are ground under the current substitution and are not
structurally equal.
(not P) succeeds when the variables of P are already determined by the positive part of the
query and no matching fact exists.
(test F A ...) invokes a declared, pure grounded predicate. All arguments must be bound
before the test is scheduled.

5.5

Set queries

union, intersect, and except combine the result spaces of subqueries. They use ordinary set union,
intersection, and relative complement.
(union
(find (Person $x) (female $x))
(find (Person $x) (male $x)))

5.6

Rule queries

A rule query contains one or more clauses:
(rules
(export path)
(<- (path $x $y)
(edge $x $y))
(<- (path $x $z)
(path $x $y)
(edge $y $z)))

The head of each clause is a relation pattern. The body is a conjunction of goals. By default
every relation appearing in a rule head is exported. An export option restricts the result to the
listed head relations while still permitting unexported helper relations inside the fixed point.

5.7

Core queries

(core C) asserts that C is a Morkql Core space expression. Core syntax is defined in Section 10.
Core programs bypass relational planning but still undergo sorting, scope, and target-version checks.

6.2

Open and strict schema modes

In open mode, an undeclared relation uses the default MORK codec for the whole atom. Arity and
domain types are inferred only from local use.
In strict mode, every relation in a query, rule head, or output template must be declared. Strict
mode is required by the Verified MORKQL profile.

6.3

Layouts

For relation R with fields f1 , . . . , fn , a layout L is an injective path template containing every field
exactly once, possibly in a different order and possibly under a different physical tag.
For example, the logical fact
(child Bob Pam)

canonical:
by-parent:

child.Bob.Pam
child-by-parent.Pam.Bob

The dot notation is explanatory; the actual codec may use structural path items.

6.4

Index coherence

A secondary index is coherent when decoding every indexed path through its declared inverse
produces exactly the same logical fact set as the canonical layout.
A conforming implementation must classify each index as one of:

MORKQL Draft Specification 0.1

13

• maintained: generated or transactionally maintained from the canonical relation by the MORKQL
runtime;
• proved: accompanied by a checked derivation of coherence;
• assumed: supplied externally and listed as a certificate assumption; or
• untrusted: usable only outside the Verified profile.

6.5

Binding modes and index choice

For every candidate plan, the compiler computes which variables are bound before a relation lookup.
It SHOULD select a layout whose longest prefix is ground under those bindings. The choice affects
cost but not denotation.
An explain plan must show both the logical relation and selected physical layout.

7

Static Semantics

7.1

Compilation environments

Static checking uses:
• a relation environment ΓR mapping relation names to field types and layouts;
• a grounded environment ΓG mapping grounded names to signatures and declared properties;
• a variable environment ΓV mapping variables to inferred types; and
• a source environment identifying the default physical space and schema.

7.2

Variable scope

Variables are scoped to the nearest find or rule clause. Variables with the same spelling in different
clauses are distinct. Rule-head variables and rule-body variables share one clause scope.
The compiler must alpha-normalize variables before planning. Generated variables must not
collide with user variables.

7.3

Range restriction

A find query is safe only if every variable in the output template occurs in a positive relation goal
or is determined by a chain of equality constraints from such a variable or a ground constant.
A rule is safe only if every variable in its head occurs in a positive body relation goal or is
similarly determined.
For example, the following query is rejected because $y is unconstrained:
(find (Pair $x $y)
(person $x))

7.4

Negation safety

Every variable in (not P) must be bound by positive goals or equalities in the same query or clause.
Negation never introduces bindings.
The compiler may reorder conjunctions, so “already bound” is a dependency condition rather
than a source-order condition.

MORKQL Draft Specification 0.1

7.5

14

Grounded tests

Every argument to test and != must be ground when the goal executes. A grounded predicate
declaration has the shape:
(morkql:grounded less-than
(type (-> Number Number Bool))
(properties pure total deterministic))

A test used by a Verified query must be declared at least pure, total, and deterministic. The
checker may require an implementation hash or proof reference.

7.6

Type checking

For a declared relation, each argument is checked against the corresponding field type. Repeated
variables impose type equality. A template is checked structurally; strict mode requires its outer
relation to be declared.
Implementations may support subtype or coercion systems, but any coercion used in a Verified
query must be explicit in the certificate.

7.7

Rule dependencies

A rule dependency graph has one node per head relation. A positive body reference adds a positive
edge; a negated body reference adds a negative edge.
A rule group is stratified when no strongly connected component contains a negative edge. Strata
are evaluated in dependency order. Relations from lower strata are constant inputs to higher strata.

7.8

Monotonicity of recursive components

A recursive strongly connected component is accepted in the Verified profile only when its immediateconsequence operator is monotone. Positive relation goals, unification, inequality over already-bound
values, and pure value tests are monotone. Negation of a relation in the same component, subtraction
depending on the current recursive value, and aggregates over the current recursive value are not
monotone.

7.9

Finite-range recursion

Monotonicity alone does not guarantee termination if rules can construct an unbounded sequence
of fresh terms. The Verified profile therefore requires a finite-range proof. The standard sufficient
condition is function-free Datalog: recursive heads may contain relation structure, variables from
positive body goals, and ground constants, but may not wrap a recursively varying term in a fresh
constructor.
A grounded operation used in recursion must additionally be declared finite-range, or the
compiler must derive an equivalent finite-domain bound.

9

Compilation to MORKL

9.1

Required stages

A conforming compiler performs the following conceptual stages:
1. parse the quoted atom as a MORKQL AST;
2. expand surface macros, including the long query form;

MORKQL Draft Specification 0.1

17

3. alpha-normalize variables and replace every $_ with a fresh variable;
4. resolve schemas, relation fields, and grounded declarations;
5. check types, safety, stratification, monotonicity, and finite range;
6. construct a logical binding plan;
7. choose physical layouts and a legal goal order;
8. lower the logical plan to Morkql Core or directly to Morkl;
9. optionally apply certified Morkl rewrites; and
10. emit code, explain information, and optionally a proof certificate.
No surface-only constructor may remain in the executable backend term.

9.2

The MQT macro

The Zippy examples define a multi-pattern query helper of the schematic form:
MQT(source, [P1, ..., Pn], template)

It successively matches each path pattern against source, carries a consistent binding environment,
and emits the instantiated template after the last pattern. Morkql adopts MQT as a compiler
macro, not as a new Morkl constructor.
The required semantic theorem is:
[[MQT(S, [P1 , . . . , Pn ], T )]] = {θ(T ) | θ(Pi ) ∈ [[S]] for all i}.
A compiler may expand MQT using nested iteration, restriction, unwrapping, intersection,
wrapping, and singleton construction, or call an existing trusted macro expander whose result is
ordinary Morkl.

9.3

Positive find lowering

After layout selection, every relation goal is a physical path pattern. A positive query lowers
schematically as:
compileD (f ind T P1 · · · Pn ) = MQT(D, [L1 (P1 ), . . . , Ln (Pn )], LT (T )),
where each Li is the selected coherent layout and LT is the output layout or default codec.
A ground, goal-free find lowers to Morkl Singleton.

9.4

Equality lowering

Variable-variable equality is normalized by union-find over compiler variables. Variable-ground
equality becomes a binding or a constant constraint. Equality that remains after normalization is
emitted as an explicit grounded structural test.
This normalization step is semantics preserving when substitutions are rewritten consistently
throughout all patterns and the template.

9.5

Inequality and grounded tests

A grounded Boolean predicate lowers to an explicit grounded Morkl boundary. One valid implementation encodes its bound arguments as a path and uses a path-to-space grounded operation that
returns {ϵ} for true and ∅ for false. The returned gate is composed with the current binding row.
The certificate must identify the grounded function and the properties assumed or proved about
it.

Safe negation lowering

Negation is compiled as an anti-join over an internal binding space.
Let B be the space of encoded substitutions produced by positive goals. Let BN be the subset
of those substitutions for which the negated pattern has a match. Then:
Bok = B \ BN .
The output template is instantiated only from Bok . This transformation uses Morkl subtraction
but does not expose binding-row encoding to the user.
Because every variable in the negated pattern is already represented in B, no new binding can
be introduced by the anti-join.

Verification and Proof-Carrying Compilation

12.1

Verification objective

For source D, surface query Q, emitted MORKL term M , schema S, and explicit assumptions A,
the central claim is:
A ⊢ [[Q]]D,S = [[M ]]path(D,S) .

MORKQL Draft Specification 0.1

23

The left side is the logical MORKQL semantics. The right side is the reference MORKL path-set
semantics over the encoded physical source.

12.2

Why the surface language helps verification

The MORKQL frontend knows facts that are difficult to recover from an arbitrary MORKL AST:
• variable binders and alpha-equivalence classes;
• relation arity and domain types;
• which goals are positive, negative, or grounded;
• which recursive dependencies are monotone;
• which physical layouts implement the same logical relation; and
• which plan changes are merely conjunction permutations.
Capturing those facts before lowering reduces verification to reusable theorems and small instance
data.

12.3

Required proof obligations

A Verified compiler must account for:
1. Parsing and macro expansion. The parsed AST corresponds to the quoted atom, and
long-form syntax expands definitionally.
2. Alpha normalization. Renaming is capture avoiding and preserves substitutions.
3. Static safety. Output, negation, and grounded inputs are range restricted and well typed.
4. Layout correctness. Every selected physical layout is coherent with the logical relation, by
maintenance, proof, or an explicit assumption.
5. Find lowering. The MQT expansion has the multi-pattern comprehension semantics.
6. Planning. Goal reordering preserves conjunction and respects dependencies.
7. Negation lowering. Binding-space subtraction implements safe anti-join.
8. Rule lowering. The union of compiled clauses is the immediate- consequence operator.
9. Fixed point. Monotonicity and finite range justify least-fixed-point iteration and termination.
10. Optimization. Every subsequent MORKL rewrite is law justified or otherwise checked against
the reference semantics.

12.5

Certificate checker

The checker should be much smaller than the optimizing compiler. It need not repeat cost estimation.
It replays structural translations, checks theorem instances, validates hashes and scoping, and verifies
every assumption against the configured trust policy.

12.6

Trusted computing base

A deployment should state its trusted computing base. At minimum it contains:
• the parser or a parser-to-AST validation step;
• the MORK atom/path codec and layout decoders;
• the MORKL reference semantics or its formal counterpart;
• the certificate checker; and
• grounded functions listed as assumptions rather than proved code.
The optimizer, cost model, and query planner need not be trusted when all their transformations
are checked.

12.7

Connection to the Zippy verification stack

The frontend certificate ends at an initial MORKL term. Existing Zippy-style proof artifacts can
then connect that term to an optimized term, zipper program, and operation graph. The intended
composed statement is:
MORKQL surface
== checked logical IR
== initial MORKL
== optimized MORKL
== zipper / operation graph
== reference path-set semantics

The equality signs denote checked semantic equivalence, not textual identity.

Verification profiles

This draft defines three profiles:
Base. Surface parsing, find, positive rules, set operators, and Core lowering. Static errors are
required; proof emission is optional.
Verified. Strict schema, safe stratified negation, declared grounded tests, monotone finite-range
recursion, coherent indexes, and a checkable compilation certificate are required.
Extended. Implementations may admit opaque grounded functions, unproved recursion, implementationspecific aggregates, or untrusted indexes, but must mark the resulting program as outside the
Verified profile.

13.8

Grounded test

With a declared pure predicate less-than:
!(morkql:q &people
(quote
(find (Minor $person)
(age $person $age)
(test less-than $age 18))))

The compiler schedules the test after $age is bound.

13.9

Transitive closure

Assume &graph contains:
(edge a b)
(edge b c)
(edge c d)

Query:
!(morkql:collect
(morkql:q &graph
(quote
(rules
(export path)
(<- (path $x $y)
(edge $x $y))
(<- (path $x $z)
(path $x $y)
(edge $y $z))))))

Result:
{ (path a b), (path a c), (path a d),
(path b c), (path b d),
(path c d) }

This rule group is positive, monotone, and finite range. It compiles to a MORKL fixed point
whose body is a union of two MQT branches.

14

Conformance

14.1

Base implementation requirements

A Base MORKQL 0.1 implementation must:
• parse the canonical ASCII surface syntax;
• implement find, the long query form, union, intersect, except, and positive rules;
• enforce variable range restriction and relation arity;
• compile all accepted queries to ordinary MORKL;
• implement the mandatory Core constructors supported by its declared MORKL target;
• provide morkql:q, morkql:collect, morkql:explain, and morkql:compile; and
• document its codec, schema mode, target version, and result-order policy.

14.2

Verified implementation requirements

A Verified implementation must additionally:
• use strict schemas for relation queries;
• check types, safe negation, stratification, monotonicity, and finite range;
• classify and validate every selected index;
• reject or explicitly declassify opaque grounded operations;

MORKQL Draft Specification 0.1

30

• emit a certificate for compile/proof; and
• provide an independently invocable certificate checker.

14.3

Determinism

Given the same normalized query, schema, target version, planner configuration, and sourceindependent statistics, a compiler should emit the same normalized plan and hashes. Runtime result
order may vary unless canonical collection is requested.

14.4

Forward compatibility

Unknown surface forms must be rejected rather than interpreted as relation patterns when they
occur in query-control position. Certificates must include language and target versions. New optional
forms should use namespaced symbols until standardized.

15

Open Design Questions

The following details are intentionally left open for implementation experiments:
1. whether the host operation can receive query atoms non-eagerly, eliminating explicit quote;
2. the canonical serialization of Core paths under the evolving MORK codec;
3. the proof-term format used to connect frontend certificates to the Zippy prover artifacts;
4. the standard schema registry and index-maintenance protocol;
5. whether aggregates belong in the surface language or only in Core and grounded declarations;
6. whether parameterized named views should be surface rules, host functions, or compiled routines;
and
7. which cost statistics can be exposed without becoming part of semantic conformance.
These questions do not affect the central semantic contract: a MORKQL query denotes a finite
set of logical results and compiles to an equivalent MORKL path-space program.

B

Compiler Correctness Skeleton

A mechanized frontend proof can be organized around the following lemmas.

Lemma 1: alpha-renaming
If Q′ ≡α Q, then [[Q′ ]]D = [[Q]]D .

Lemma 2: MQT induction
For any finite list of positive patterns P⃗ and template T , the expansion of MQT(D, P⃗ , T ) equals the
set of consistently instantiated templates. The proof is by induction on P⃗ .

Lemma 3: conjunction permutation
For pure positive goals, any permutation preserves the satisfying substitution set. Dependencyrespecting movement of tests and negation preserves the same result.

MORKQL Draft Specification 0.1

32

Lemma 4: layout substitution
If layout L is coherent for relation R, replacing a logical R lookup by L and applying its inverse
field mapping preserves matching substitutions.

Lemma 5: anti-join
For safe negation, subtracting binding rows that extend to a match of the negated pattern yields
exactly the substitutions satisfying logical negation.

Lemma 6: rule consequence
The union of clause-level MQT expansions denotes the immediate-consequence operator TP,D .

Lemma 7: fixed point
If TP,D is monotone and finite range, inflationary iteration from I0 terminates at lfp I. I0 ∪ TP,D (I).

Theorem: frontend correctness
Combining Lemmas 1–7 with structural induction over set-query forms gives:
[[Q]]D,S = [[compile(Q, S)]]path(D,S) .
This theorem ends at the initial MORKL term. Certified MORKL rewrite and executor equivalence results may be composed afterward.

D

Glossary

Atom. A logical MeTTa value or expression used as a fact, pattern, or result.
Binding row. An internal encoded substitution used while compiling joins and anti-joins.
Codec. The injective mapping between supported logical atoms and MORK paths.
Coherent index. A physical layout representing exactly the same logical fact set as the canonical
layout.
Core. The lossless MORKQL syntax that maps one-to-one to MORKL constructors.
Layout. A physical path template for a logical relation.
MQT. The compiler macro that matches multiple patterns with consistent bindings and emits a
template.
Path. A finite word over MORK path items.
Space. A finite set of paths, stored or virtual.
Stratum. A layer of a rule program evaluated after all negatively referenced lower layers.
Virtual view. A result space navigated through MORKL or zipper operations without mandatory
eager materialization.
