## VM2 proto-hive container recovery (10:31–10:52 PDT)

Ben reported Protomega and ProtoCosmo unresponsive. Diagnosis: container
process-exhausted (hundreds of leaked PeTTa/SWI zombie processes from
responder timeout cascade). `docker exec` failing with "procReady not
received."

**Fix:** Ben ran `docker restart proto-hive` from VM2 root shell. Container
came back healthy in ~90s. All three identities (protocosmo, protomega,
protomega2) status=active. Process count normalized to ~18.

**Root cause of zombies:** Each failed `omega_case_responder.py` call (300s
timeout) left PeTTa/SWI child processes behind. Over ~14h, hundreds
accumulated. pids_limit=512 was already in place but the cascade from
repeated Codex timeouts was the actual source.

## Protomega TG responder model fix (11:05–11:20 PDT)

**Root cause of TG hang:** Protomega's `protomega_controller_compat.py`
hardcoded `--model openai/gpt-5.6-terra` for the responder. This model
uses `api: "openai-chatgpt-responses"` in the OpenClaw config, which
requires the Codex app-server. The Codex path was failing silently (240s
startup timeouts, no model calls logged), causing every responder to hang
for 300s then timeout. The anthropic fallback was never reached because
the gateway didn't have an explicit anthropic provider entry (though it
was available at runtime).

**Fix applied:** Changed model from `openai/gpt-5.6-terra` to
`anthropic/claude-opus-4-6` in `protomega_controller_compat.py` on VM2
(same model protomega2 uses successfully). Backup:
`protomega_controller_compat.py.bak.20260905T1900Z`.

**Verification:** After killing all old protomega processes and letting
the supervisor restart:
- New responder uses `--model anthropic/claude-opus-4-6` ✅
- Model calls succeeding: claude-opus-4-6 and claude-fable-5, all
  status=200, ~2-7s latency (vs. 0 successful calls before)
- Process count: 18 (healthy)
- No zombie PeTTa accumulation
- Only one PeTTa/SWI pair per responder invocation (vs. 5+ before)

**Remaining:** End-to-end canary — Ben DMs @Protomegabot and confirms a
reply arrives. The responder is actively processing (model calls every
few seconds) but the PeTTa reasoning loop may still approach the 300s
timeout for complex messages. If it does, the fix is to reduce
max-rounds or increase parallelism, not revert to the broken Codex path.

## Protomega2 JSON envelope leak fix (11:05 PDT)

**Root cause:** `clean_rendered_answer()` in protomega2's
`phase6_private_canary_runner.py` didn't detect or unwrap
`omegaclaw.action.v1` JSON envelopes. Raw JSON like
`{"protocol":"omegaclaw.action.v1","reply":{"text":"..."},"actions":[],...}`
was sent to Telegram verbatim.

**Fix applied:** Patched `clean_rendered_answer()` to detect and unwrap
omegaclaw.action.v1 JSON envelopes — both direct (`{...}` at top level)
and nested (JSON envelope inside a `(send "...")` action). Backup:
`.bak.20260905T1800Z`. Syntax verified with py_compile.

**Activation:** Protomega2 has no persistent runner — the agent_worker
spawns a fresh runner per message, so the patched code loads on the next
message automatically. No restart needed.
