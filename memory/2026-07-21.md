### Pod disappearance root cause identified and fixed

- **Root cause:** CLI `runpodctl pod create --image ...` does NOT inherit the
  template's `/start.sh`, ports, or env vars. When the main process exits, the
  pod has no keep-alive mechanism and disappears from default `pod list`.
  Web-UI-created pods use templates that bundle image + start command + ports +
  env, so they stay alive.
- **Fix:** Always use `--template-id runpod-torch-v280` instead of `--image`.
  Confirmed empirically: pod `sq84o8cnn5cwax` launched with `--template-id`
  stayed alive and SSH-reachable.
- **Correct pod creation flags:** `--template-id runpod-torch-v280`,
  `--cloud-type SECURE`, `--container-disk-in-gb 50`, `--ports "8888/http,22/tcp"`,
  `--ssh`. A100-SXM4-80GB preferred ($1.49/hr).
- **REMOTE_JOB.md MUST be written and marked APPROVED BEFORE launching any pod.**
  The heartbeat scans for REMOTE_JOB.md to verify approval; without it (or with
  "awaiting approval" text), the heartbeat deletes the pod. Proven: the 12k
  pod `mfwzq6j4z7acob` was deleted by ProtoCosmo heartbeat because the
  REMOTE_JOB.md still said "awaiting approval" even though Ben had approved
  via Telegram. Fix: always update REMOTE_JOB.md approval status to
  **APPROVED** with the timestamp and quote before launching.
- **Heartbeat uptime detector is broken:** `uptimeSeconds: 0` from RunPod API
  even for healthy pods. Do not trust it for deletion decisions. Fix queued
  per Ben's request.
