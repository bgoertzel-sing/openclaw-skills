    Scope. This document proposes a shared communication control plane for the current two-agent
    proto-hive, consisting of an OpenClaw agent with extensive skills (Protocosmobot) and an OmegaClaw
    agent that uses the OpenClaw gateway. Both agents currently use smart-ish model routers. The
    design extends this setup with event admission, responder arbitration, deduplication, private bot-
    to-bot review, update aggregation, and output governance. The preferred shared pre-inference
    placement is treated as an empirical deployment question rather than an assumption; distributed
    and weak-fallback topologies are specified. The revision also adds governor-cost budgets, thread-level
    ownership hysteresis, an explicit semantic firewall for egress processing, predeclared activation gates,
    and a human override grammar. It describes how the architecture can scale to a richer OmegaHive
    spanning many agents and both AI-only and mixed human/AI channels.

1 Executive Summary
The current proto-hive contains two powerful but partially overlapping conversational actors:

• Protocosmobot, an OpenClaw agent with broad operational skills, tools, project access, cron
  workers, and the ability to inspect and modify external state.

• OmegaClaw, a more reflective or synthetic agent that uses the OpenClaw gateway and can provide
  deeper conceptual analysis, criticism, and long-form reasoning.

• Each agent has a smart-ish router that chooses which language model should answer a given message.

This arrangement has substantial functional value, but its present communication dynamics allow
avoidable token use and noise. The major waste is not simply that useful answers are occasionally too
long. A larger problem is that the system often creates messages that should never have been generated:
acknowledgments of acknowledgments, reactions to status messages, narration of tool use, repeated error
traces, duplicate explanations, visible NO_REPLY messages, and multiple public answers to one event.
The proposed solution is a shared OmegaHive Conversation Governor (OCG) placed, where the actual
runtime permits, at a common boundary before model selection and after model generation. The existence
of a truly shared pre-inference boundary must be established during repository and runtime discovery. If
it does not exist, the same policy is implemented through per-agent local governors coordinated by a
shared durable ledger, or through a weaker ingress/egress fallback that still prevents duplicate public
output. The governor adds two control surfaces:

 1. An ingress and admission governor decides whether any agent or language model should be
    invoked, which agent owns the public response, whether a private reviewer is useful, and what output
    contract applies.

 2. An egress governor suppresses no-op output, rejects duplicates, assembles multipart responses,
    enforces response contracts, and prevents operational chatter from becoming public conversation.

The smart router is correspondingly expanded. Instead of choosing only among language models, it
chooses among actions:
          DROP | LOG_ONLY | TEMPLATE | CHEAP_MODEL | NORMAL_MODEL | DEEP_MODEL
The most important consequence is that many events terminate before any LLM call. A receipt, duplicate
system event, repeated cron status, sibling echo, or non-addressed bot message can be recorded without
invoking a model or posting a reply.
For the current two-agent system, the default responsibility split is:

• Protocosmobot is the execution and evidence agent. Its tools and workers emit structured facts,
  artifacts, blockers, approvals, and state changes.

• OmegaClaw is the synthesis and reasoning agent. It receives compact state plus selected evidence
  rather than raw operational streams.

• The governor grants exactly one public response lease per event or task state. A second agent may
  act as a private reviewer, but does not independently answer the human unless explicitly invited.

The proposed architecture preserves utility because it does not force all reasoning to become short
or shallow. Deep analysis remains available when requested or justified. The design instead removes

redundant invocations, moves operational detail into durable artifacts and logs, makes silence an actual
control action, and uses progressive disclosure for optional detail. It is activated conservatively: Phase 0 is
instrumentation only, Phase 1 computes shadow decisions without changing delivery, and no suppression
or topology-changing behavior is enabled until replay and live shadow data quantify false-silence risk,
governor overhead, and projected net savings, followed by explicit human approval. The egress governor
may perform formatting and other demonstrably non-semantic transformations, but it is forbidden from
silently adding, deleting, or altering substantive claims.
For a larger OmegaHive, the same principles generalize into a multi-channel communication fabric with:

• typed channels and privacy labels;

• topic- and role-based subscriptions;

• local channel governors coordinated by a global event ledger;

• internal AI-only deliberation rooms;

• mixed human/AI rooms with one or more designated public spokesagents;

• bounded review committees rather than uncontrolled many-agent reply cascades;

• attention budgets, response leases, incident aggregation, and durable handoff artifacts.

The implementation can be staged safely. The first deployment should run in shadow mode, recording
what would have been suppressed without actually suppressing anything. Once false-silence rates are
acceptably low, deterministic no-op suppression and repeated-event coalescing can be activated, followed
by shared response leases, private review requests, daily digest aggregation, and eventually multi-channel
OmegaHive federation.


2 Motivation and Empirical Problem
2.1 The key distinction: verbosity versus message creation
There are two separable sources of token waste:

 1. Essay amplification: a useful response is longer than necessary for the immediate decision.

 2. Message amplification: a response is generated even though no response was needed, or several
    agents respond to the same event.

Length limits and concise prompting primarily address essay amplification. They are useful, but they do
not address the larger structural failure modes. A bot that generates NO_REPLY, “noted,” or “nothing
to add” has already consumed model tokens. If this text is then posted into a shared channel, it can
provoke another agent to spend tokens interpreting and acknowledging it.
The central design principle is therefore:
      The cheapest and least noisy response is not a shorter LLM response. It is a
      correctly suppressed LLM invocation and no outbound message.

2.2 Observed failure classes in the current proto-hive
The transcripts exhibit recurring classes of behavior that are individually understandable but collectively
expensive:
Acknowledgment loops
                           One agent says “noted,” another acknowledges the note, and the first confirms
                           that the acknowledgment is already covered.
Visible silence markers
                       A bot outputs NO_REPLY, “staying quiet,” or “nothing to add” into the channel
                        instead of returning an internal no-send status.
Parallel public answers
                       Protocosmobot and OmegaClaw each answer the same human message, often
                       with overlapping substance.
Tool narration             Internal steps such as “let me inspect,” “continuing provisioning,” or “now I
                           will retry” are posted as public conversational messages.
System-event echoing Full stack traces, fallback notices, or cron failures are repeatedly injected into
                     a channel and repeatedly analyzed.
State reconstruction       A stateless worker rereads broad context and re-explains project history rather
                           than consuming a compact current-state object.
Channel and identity confusion
                      An agent responds to a message meant for another agent, answers a question
                      from a different project, or treats system metadata as a request.
Promise loops              A bot repeatedly announces that it is reading or preparing a result but does
                           not deliver a concrete artifact.
Speculative prose before cheap verification
                       Several paragraphs are produced about an operational uncertainty that could
                       have been resolved by a simple file, process, commit, or job-status check.
Over-reporting incremental progress
                     Small test-count increases, routine commits, or “no material change” updates
                     are sent many times per day.
These behaviors do not imply poor underlying reasoning. They arise because the current architecture
gives each agent an incomplete local view and asks each model invocation to decide both whether to
respond and what to say. The result is a conversational tragedy of the commons: locally reasonable
agents jointly produce global noise.

2.3 Why prompt-only fixes are insufficient
Both agents should receive stronger communication instructions, but prompts alone cannot reliably
enforce system-wide invariants:

• An agent cannot know that a sibling already claimed a message unless there is shared state.

• A model cannot save the tokens used to decide that it should say NO_REPLY; only pre-inference
  admission can do that.

• Retry and reconnect events may cause the same input to be processed more than once unless
  idempotency is enforced outside the model.

• A model may correctly identify an echo loop and still produce another message explaining the echo
  loop.

• Independent routers may both choose a sensible model for the same event; they need a shared
  arbitration layer, not merely better model selection.

The proposed governor therefore treats communication discipline as a first-class control-plane problem.


3 Goals, Non-Goals, and Design Principles
3.1 Primary goals
The system should:

 1. Reduce total model input and output tokens without materially reducing useful functionality.

 2. Prevent duplicate or no-op public messages before they are generated.

 3. Preserve the value of having both an operational agent and a reflective reasoning agent.

 4. Ensure one clear public answer by default, even when multiple agents contribute internally.

 5. Aggregate routine project progress into compact, meaningful updates.

 6. Keep detailed evidence and reasoning in durable artifacts rather than repeatedly regenerating it in
    chat.

 7. Improve traceability: every public response should have a clear triggering event, owner, state version,
    and rationale.

 8. Scale from the present two-agent proto-hive to a larger OmegaHive with many channels and agents.

3.2 Non-goals
The design is not intended to:

• force all answers into a uniformly short style;

• prevent rich philosophical, scientific, or technical dialogue when that dialogue is the point;

• replace agent-specific personalities, skills, or model routers;

• centralize all cognition in one monolithic controller;

• hide consequential disagreement among agents;

• prevent humans from explicitly requesting multiple independent answers;

• make the system silent merely to optimize cost.

3.3 Core design principles
 1. Admission before inference. Decide whether an LLM call is needed before selecting a model.

 2. One public owner, many private contributors. Multiple agents may assist, but one agent
    normally holds the public response lease.

 3. Silence is a real action. No-send is structured control output, never user-visible prose.

 4. Delta over narrative. Communicate changed state, decisions, blockers, and evidence; do not
    reconstruct unchanged history.

 5. Probe before prose. Resolve cheap operational uncertainties before writing extensive analysis.

 6. Artifacts carry depth. Chat carries summaries, decisions, and pointers; durable files carry long
    reasoning and evidence.

 7. Stateful infrastructure, stateless models. Models may remain replaceable and session-local
    while the communication fabric maintains durable event, task, and project state.

 8. Fail open for usefulness only where safe. Early deployment should prefer logging and shadow
    decisions over aggressive suppression; suppression becomes stricter only after measurement.

 9. Human intent is authoritative. Explicit user addressing, request for multiple viewpoints, or
    request for live updates overrides default quietness policies.

5.2 Logical architecture versus physical placement
The diagram above describes logical responsibilities, not a guaranteed single-process deployment. In

object, lease protocol, audit schema, and channel policy should operate across all three placements. This
prevents repository discovery from forcing a redesign of the policy model.

5.3 Control plane versus cognition plane
The governor belongs to the control plane. It does not need to solve the user task. Its job is to decide:

• whether the event should cause any inference;

• which agent is responsible;

• whether a private review is warranted;

• how much context is needed;

• what cost and length budget applies;

• whether the output may be sent.

Protocosmobot and OmegaClaw remain in the cognition and action plane. They perform tools,
reason, synthesize, and create artifacts. This separation is important because communication admission
should be deterministic where possible, cheap, auditable, and shared across agents.

6.3 Addressing, ownership, and response leases
6.3.1 Ownership precedence and conversational hysteresis
The governor should resolve ownership in the following precedence order:

 1. Explicit human address or explicit human override such as /solo @agent.

 2. Explicit delegation or handoff recorded in task state.

 3. Existing active task- or thread-level response lease.

 4. Assigned project or task owner.

 5. Agent whose message is being directly replied to, when the reply remains within the same task.

 6. Capability match:

     • operational, filesystem, code, process, experiment, and tool questions to Protocosmobot;

     • synthesis, critique, philosophy, theory, and long-form explanation to OmegaClaw.

 7. Conversational stickiness or recent-speaker bias within a short inactivity window.

 8. Channel-specific default spokesperson.

 9. Tie-break by current load, confidence, or deterministic precedence.

The active owner should normally remain sticky for the life of a conversational task or for a short timeout
such as ten minutes of inactivity. This prevents rapid human dialogue from alternating voices message
by message. Stickiness is broken by explicit re-addressing, explicit delegation, task change, capability
boundary, lease expiration, owner failure, or a high-severity override.

leases, but the exception should be deliberate, scoped, logged, and visible. The default scope of an “all

6.5 Idempotency and duplicate detection
6.5.1 Exact idempotency
The gateway should record handled event IDs and source message IDs. A retry or reconnect must
preserve a retry_of_event_id link. Exact duplicates are dropped without model use.
A useful key is:
           (project_id, task_id, event_type, state_version, intended_recipient)
Only one public response should normally be emitted for this key.

6.5.2 Near-duplicate and novelty detection
Exact hashes are insufficient because agents often restate the same content with different wording.
However, embeddings and model classifiers are not free. Novelty detection must use a cost-ordered
cascade and should call expensive mechanisms only for ambiguous cases.

 1. Exact event ID, retry link, source message ID, and normalized payload hash.

 2. Structured state checks: task, state version, incident state, requested action, evidence references,
    and numerical-result changes.

 3. Cheap lexical or token-set similarity within a bounded recent thread window.

 4. Cached semantic fingerprints or local embeddings when prior stages remain ambiguous.

 5. A small model classifier only for high-value cases where an incorrect decision would be costly and
    deterministic evidence is insufficient.

A provisional feature representation may include:
 semantic_distance
 new_fact_fraction
 state_version_changed
 new_action_or_decision
 new_evidence_reference
 new_number_or_result
 explicit_correction
 severity_and_bypass_flags


The first implementation may initialize a weighted score for shadow analysis, but no particular weights
should be treated as justified constants. Weights, thresholds, or an alternative decision tree must be
calibrated from replay labels and Phase 1 live shadow data. The calibration objective is not maximum
suppression; it is high useful-information retention at favorable net cost.
A message with no new fact, no state change, no new action, and no protocol-relevant acknowledgment
is a strong suppression candidate even when its wording differs. Conversely, a similar-looking message
with a new caveat, changed number, changed evidence, explicit correction, or new requested action must
be preserved.
Semantic duplicate detection remains shadow-only until the evaluation set demonstrates a sufficiently
low false-silence rate. Deterministic exact control values such as structured NO_SEND may be handled
earlier.

6.6.1 Governor cost cascade and budget
The extended router must account for the cost of governing. It should never spend a model call and
hundreds of tokens deciding whether to suppress a tiny acknowledgment that deterministic metadata
could classify. Every policy stage records its own CPU time, model calls, tokens, cache hits, and latency.
The preferred rule is:
      Use the cheapest decision procedure that can safely resolve the event. Escalate to embeddings
      or a classifier only when the expected downstream savings and false-silence risk justify the
      added cost.
The router should enforce a configurable overhead budget and expose the net-efficiency ratio defined in
Section 13. A candidate classifier that consumes more resources than it saves should remain disabled
even if it is accurate.

serialized into a human-visible channel. Exact sentinels can therefore be suppressed deterministically

An acknowledgment-like candidate may be suppressed only when all of the following hold:

 1. it introduces no new fact, caveat, evidence, or correction;

 2. it records no consequential state transition;

 3. it requests no action and creates no commitment;

 4. it is not required by a safety, authority, cost, ownership, or handoff protocol;

 5. the human did not explicitly request acknowledgment.

Consequential acknowledgments should preferably become structured state events such as ownership_accepted,
budget_cap_accepted, shutdown_confirmed, or handoff_accepted. Channel policy can decide whether
such a state transition also deserves a concise visible confirmation.

6.12.2 Semantic firewall for egress processing
The egress governor is a control-plane component, not an unaccountable co-author. It may perform only
transformations that are demonstrably non-semantic or mechanically verifiable, including:

• stripping internal control sentinels;

• removing clearly marked tool narration or debug metadata;

• normalizing formatting;

• assembling multipart messages;

• removing byte-identical or paragraph-identical repetition;

• enforcing transport framing and size limits;

• moving detailed evidence to a referenced artifact without deleting the summary or caveat required
  by the response contract.

It must not silently add, delete, weaken, strengthen, or alter factual claims, recommendations, uncertainty
statements, safety caveats, commitments, or requested actions. If a candidate violates a substantive
response contract, the governor returns a structured REGENERATE request to the originating agent. A
small repair model may be used only for a tightly constrained non-semantic transform whose output can
be verified against the original.

7.1 Protocosmobot as execution and evidence agent
Protocosmobot should remain the primary agent for:

• code, filesystem, repository, process, and infrastructure work;

• experiments and project workers;

• evidence gathering and verification;

• creating and modifying artifacts;

• operational status and approval requests.

Its tools and skills should return structured internal results by default. Public prose should be generated
only after the governor classifies the event as human-visible.
Protocosmobot’s local policy should include:

 1. Perform ordinary tool sequences silently.

 2. Do not narrate each command, retry, file lookup, or provisioning step.

7.2 OmegaClaw as synthesis and reasoning agent
OmegaClaw should normally receive curated context rather than the raw activity stream. It is well

• conceptual synthesis;

• criticism and alternative interpretations;

• scientific and philosophical analysis;

• prioritization among options;

• converting structured evidence into a human-readable conclusion;

• long-form writing when requested.

Its local communication policy should include:

1. Do not paraphrase operational updates merely to show comprehension.

2. Do not acknowledge sibling messages unless acknowledgment changes shared state.

3. Do not answer a task owned by Protocosmobot unless assigned as reviewer or explicitly addressed.

4. Return compact private reviews when acting as reviewer.

5. Prefer a conclusion, strongest reasons, uncertainty, and recommendation over a broad essay.

6. Put durable deep treatments into artifacts and post a short pointer in chat.

7. Do not routinely end with an unsolicited proposal to create another formalization, paper, or project.

Both agents should contribute when the task combines operational evidence and difficult interpretation.

• interpreting an experiment result;

12 Failure Modes and Safety Considerations
12.1 False silence
The largest risk is suppressing a message that contained a useful warning or correction. Mitigations
include:

• shadow-mode deployment;

• conservative deterministic suppression first;

• bypass for safety, security, authority, cost, and explicit human addressing;

• logging every suppression decision with reason codes;

• easy human command to inspect suppressed events;

• periodic audit samples reviewed by a strong model or human.

12.2 Over-centralization
A shared governor can become a bottleneck or single point of failure. The design should therefore:

• keep the governor policy-driven and relatively simple;

• preserve direct emergency paths for high-severity agents;

• use durable event logs so decisions can be replayed;

• allow local channel governors in a larger hive;

• avoid embedding substantive domain reasoning in the governor.

12.3 Lease deadlock or abandonment
An agent may acquire a lease and fail. Leases need timeouts, heartbeats only while real work is underway,
and deterministic reassignment. A lease expiration should not itself generate public chatter.

12.4 Semantic deduplication errors
Two messages may be semantically similar but differ in an important caveat. Early semantic suppression
should therefore operate in shadow mode or require strong confidence. New numerical evidence, changed
state version, changed requested action, explicit correction, or high-severity flags should override semantic
similarity.

12.5 Private review leakage
AI-only channels may contain speculative, sensitive, or low-confidence material. Egress must enforce pri-
vacy labels and ensure that public synthesis does not expose internal-only content without authorization.

12.6 Human confusion about who answered
The public response should clearly retain the identity of the designated agent. Internal reviewers can be
credited when useful, but the system should not blur agent identity or create the appearance that one
bot performed another bot’s tools.

12.7 Governor overhead and negative savings
The governor can become wasteful if it routinely invokes embeddings or classifiers for trivial events.
Mitigation requires a cost-ordered decision cascade, cache reuse, per-stage metrics, and an explicit
net-savings gate. Expensive novelty logic remains off when deterministic metadata resolves the event or
when projected savings do not exceed overhead by the configured margin.

12.8 Ownership thrashing
Per-event owner resolution may alternate voices during rapid dialogue. Thread- and task-level hysteresis,
explicit lease-break rules, and the ownership precedence order prevent disjointed conversation. Stickiness
must not override explicit human address, delegation, capability boundaries, or high-severity intervention.

12.9 Semantic mutation by the governor
An egress repair model could quietly change the originating agent’s meaning. The semantic firewall
prohibits substantive rewriting. Non-semantic transforms must be verifiable; otherwise the candidate is
returned for regeneration. Audit records preserve the original candidate, transformation type, and final
output.

13.2 Predeclared activation and go/no-go gates
Before Phase 0 data are inspected, define the decision criteria for each active feature. The exact numerical
thresholds may be adjusted to the system’s traffic volume, but they should be declared before activation
to avoid post-hoc justification.
At minimum, activation requires:

• a material measured no-op, duplicate, incident-amplification, or parallel-response problem for the
  feature being enabled;

• projected avoided cost substantially greater than governor overhead;

• replay and live shadow estimates of false silence below the approved threshold for the relevant event
  class;

• no material degradation in time to useful answer or human-rated useful-information retention;

• explicit human approval for the feature flag and channel scope.

A feature can be rejected while simpler features proceed. For example, semantic embedding-based
suppression may fail its economics gate even though structured NO_SEND, own-message filtering, incident
coalescing, and response leases remain strongly justified.

14 Deployment and Migration Strategy
14.1 Phase 0: baseline instrumentation only
Add event IDs, origin metadata, model-call counters, token estimates, outbound-message fingerprints,
governor-stage timing, and channel/task ownership observations without changing dispatch, delivery,
suppression, or topology. Instrumentation taps and durable logs are allowed; live rerouting and public-
output changes are not.
Before reviewing the results, record the go/no-go criteria for each later feature. Phase 0 must run
long enough and collect enough varied events to cover direct human questions, bot-bot exchanges, cron
updates, errors, attachments, approval requests, urgent alerts, and long-running tasks.

14.2 Phase 1: shadow decisions and false-silence audit
Run admission, ownership, incident, response-contract, semantic-firewall, and egress decisions in parallel
with current behavior. Record what would have been suppressed, aggregated, rerouted, privately
reviewed, or regenerated. No shadow decision changes production behavior.
Audit false-silence candidates by category, calibrate novelty features and thresholds, quantify governor
overhead, and estimate net savings. The shadow period should be bounded by both elapsed time and
minimum event coverage, not merely one calendar day.

14.3 Activation Gate 1: explicit approval
At the end of Phase 1, produce a decision report containing baseline rates, shadow confusion matrices,
false-silence examples, governor overhead, projected net savings, topology finding, and proposed feature
scopes. No live suppression, lease enforcement, topology change, or semantic novelty activation occurs
until the human operator explicitly approves the named flags and channel scope.

14.4 Phase 2: deterministic suppression
Activate only approved, high-confidence deterministic classes:

• suppress exact structured NO_SEND control results;

• block own-message loopback and exact retry duplicates;

• suppress acknowledgment-like prose only when structured novelty and protocol-state checks confirm
  no consequential transition;

• coalesce exact repeated incidents;

• stop public tool-step narration from known worker event types;

• aggregate “no material change” project updates.

Maintain a one-switch rollback and a human-visible suppression-inspection command.

14.5 Phase 3: shared response leases with hysteresis
Enable a single public owner per task or thread with conversational hysteresis. Begin with mixed
human/AI project channels. Preserve explicit multi-agent requests and verify that rapid human dialogue
does not cause owner thrashing.

14.6 Phase 4: private review bus
Move routine bot-to-bot critiques and evidence requests off Telegram. Bound reviews by question, time,
and response length.

14.7 Phase 5: daily digest and compact project state

14.8 Phase 6: calibrated semantic novelty and adaptive budgets

and model budgets based on message class, project risk, and human preferences.

17 Conclusion
The present proto-hive does not need less intelligence. It needs a communication substrate that makes
intelligence selective about when to speak, who should speak, and what information belongs in public
conversation.
The highest-value change is to move response admission, ownership, idempotency, update aggregation,
and no-op suppression into a shared gateway-level governor. Agent prompts and length limits remain
useful, but they become the final layer of refinement rather than the sole mechanism of control.
The architecture preserves the useful asymmetry between Protocosmobot and OmegaClaw: one gathers
evidence and acts; the other synthesizes and critiques. Their collaboration becomes private, targeted,
and bounded, while humans normally receive one coherent answer. This conclusion does not depend on a
single physical deployment topology: centralized and coordinated-local placements share the same policy
and ledger semantics. The governor itself remains cost-bounded, shadow-tested, explicitly activated, and
barred from silently rewriting substantive cognition-plane content. Routine project activity becomes
durable state plus one daily digest. Errors become incidents rather than repeated conversational events.
Silence becomes a real action. Deep reasoning remains available when it is genuinely useful.
The same design scales naturally to a larger OmegaHive by federating channel governors around a shared
identity and event ledger, separating internal AI deliberation from human-visible output, and using
explicit spokesagents, response leases, attention budgets, and boundary brokers.

A.7 Phase E: hard no-op suppression
Activate only deterministic egress suppression behind a feature flag.

A.7.1 Initial suppression classes
• exact NO_REPLY;

• exact or near-exact acknowledgment-like prose only when it carries no new claim, evidence, action,
  commitment, or consequential protocol state;

• “staying quiet,” “nothing to add,” and “already covered” under the same structured no-delta test;

• own outbound message loopback;

• exact repeated system-event payloads;

• known intermediate tool-progress event types.

A.7.2 Required safeguards
• Never suppress explicit human messages.

• Never suppress safety, security, cost, authority, or irreversible-action alerts.

• Log candidate text and reason privately.

• Provide a command to inspect recent suppressed messages.

• Provide a single feature flag to disable all active suppression.

• Preserve acknowledgments that accept ownership, a budget or safety constraint, a handoff, shutdown,
  or another consequential state transition.

• Apply no substantive egress rewriting; contract failures regenerate at the source agent.

A.7.3 Acceptance criteria
• Replay corpus shows no regression in explicit human answers.

• Live canary produces no known false silence for the approved observation window.

• Token and message counts decline measurably after governor overhead is deducted.

• Human override commands and suppression-inspection commands work in the canary channel.

D Future Research Directions
Once the practical governor is stable, the event log enables deeper study of multi-agent communication:

• learning policies that optimize useful information per token rather than brevity alone;

• estimating marginal value of an additional reviewer;

• detecting conversational attractors such as acknowledgment loops and status spirals;

• attention allocation as a market or ECAN-like process;

• causal attribution of which agent contribution improved the final answer;

• adaptive committee formation based on task novelty and risk;

• formal safety properties for one-response leases and privacy boundaries;

• modeling the governor as an OmegaHive social-regulation layer rather than a mere cost-control
  mechanism;

• formalizing acknowledgment loops as zero-information conversational attractors;

• interpreting leases as mutual-exclusion invariants over shared conversational attention;

• connecting novelty and expected information gain to ECAN-style attention allocation and Hyperseed
  representations.

The most important research stance is that low-noise communication should be evaluated as a form
of functional coordination, not cosmetic concision. The desired system speaks less because it routes
attention and responsibility better, not because its agents have less to contribute.
