A Hyperon-Ready Python Architecture for the Chaos Language
Algorithm
Ben Goertzel and Collaborators
July 3, 2026

Abstract
This document proposes an elegant Python library architecture for the Chaos Language
Algorithm (CLA). The goal is to start with a simple, usable, pure-Python implementation,
while arranging the abstractions so that later versions can move clustering, categorization,
pattern mining, grammatical search, and scoring into Hyperon/Atomspace/MeTTa without a
major rewrite. The central architectural idea is to separate the stable CLA domain model from
replaceable reasoning backends. The stable domain model contains symbols, chunks, categories,
rules, grammars, edits, proposals, parse objects, and MDL scores. The replaceable backends
implement pattern mining, category induction, grammar search, scoring, persistence, and fact
querying. A backend-neutral fact layer provides the migration path from ordinary Python
dictionaries and counters to Atomspace-based AI algorithms.

Purpose and Audience

This document has two audiences.
(a) Human designers of the CLA software stack, who need a clear and durable decomposition of
concepts.
(b) Coding agents that will implement the first working library and later extend it toward Hyperon/Atomspace integration.
The guiding goal is not to make the first version maximally clever. The guiding goal is to make
the first version simple, correct, useful, and hard to paint into a corner. The design should permit
a migration path from a pure-Python symbolic grammar induction library to a Hyperon-backed
cognitive grammar induction substrate.

2

Background: CLA and the Key Distinction

The Chaos Language Algorithm begins with a continuous or discrete time series, converts it into a
symbolic string, and searches for a compact, predictive grammar explaining the resulting symbolic
dynamics. The library design in this document assumes the corrected CLA distinction between two
orthogonal forms of compression:
Chunking. A chunk or nonterminal abbreviates a recurring sequence. If a sequence β recurs often,
one may introduce a production N → β and rewrite occurrences of β as N . This is sequential,
syntagmatic, “and-then” compression.
Categorization. A meta-symbol or category abbreviates a set of mutually substitutable tokens.
If tokens v1 , . . . , vk occur in sufficiently similar contexts, one may introduce a category M =
{v1 , . . . , vk } and write rules using M as a slot. This is paradigmatic, “either-or” compression.
This distinction must be preserved in the code. It is the most important conceptual guardrail
for the library.

3

Invariant 1 (Chunk-category separation). A chunk token is defined by a production N → β, where
β is a sequence. A category token is defined by a set of substitutable members M = {v1 , . . . , vk }. A
category is not a compressed sequence, and a chunk is not a substitutability class.

3

Design Thesis

The CLA library should have three layers:
+--------------------------------------------------------------+
| User API: Pipeline, fit(), transform(), predict(), explain() |
+--------------------------------------------------------------+
| Domain Core: Corpus, Token, Grammar, Category, Edit, Score
|
+--------------------------------------------------------------+
| Backends: memory, JSON, SQLite, NumPy, sklearn, Hyperon
|
+--------------------------------------------------------------+
The domain core is deliberately boring. It contains typed, deterministic Python data structures
and pure transformations. The backend layer is where intelligence lives. In the first version, backends
can use simple counters, n-gram scans, context vectors, greedy search, and approximate MDL
scoring. Later, the same interfaces can be implemented using Hyperon Atomspaces, MeTTa pattern
matching, PLN-like inference, metagraph rewrite search, or other cognitive methods.
Design Principle 1 (Backend neutrality). The core CLA objects should not know how patterns
were discovered. A chunk proposal may come from a Python n-gram counter, a SEQUITUR-like
routine, an information-theoretic search, a Hyperon query, or a remote agent. The core induction
loop should see all of these as typed Proposal objects.
Design Principle 2 (Optional Hyperon). Hyperon integration should be an optional adapter package, not a core runtime dependency. The first implementation should be installable and testable
without native Hyperon bindings, DAS, MeTTa, or any external Atomspace service.

Core Conceptual Model

The library should expose a small number of central concepts.
Corpus. A symbolic sequence, or a collection of sequences, with optional metadata about the
trajectory, source system, sampling interval, or partition.
4

Token. Something that can occur in a rewritten sequence. Tokens include base symbols, chunk
tokens, and category tokens.
Base symbol. A token corresponding to an original cell in the symbolic partition.
Chunk or nonterminal. A token defined by a production N → β, where β is a sequence of tokens.
Meta-symbol or category. A token-like class defined by a member set M = {v1 , . . . , vk }. The
members are tokens that can fill the same slot in a rule.
Production. A grammar rule, typically of the form N → β, where β is a sequence of tokens and
category slots.
Grammar state. The current vocabulary, rules, categories, rewritten corpus, score cache, parse
information, and edit log.
Proposal. A possible change to the grammar state, such as adding a chunk, adding a category,
merging categories, splitting a category, or pruning an unused rule.
Edit. A committed or commit-ready state transformation.
Score. A two-part description-length score,
L(G, S) = L(G) + L(S | G),
where L(G) is the model cost and L(S | G) is the cost of encoding the data given the grammar.

Edits and Proposals

The induction engine should not mutate a grammar directly. It should choose typed edits and apply
them through a controlled edit applier. This provides reproducibility, rollback, distributed search,
backend neutrality, and a clean path to Hyperon-backed search.

11.1

MVP Components

NGramPatternMiner. Counts repeated n-grams up to a maximum length and proposes AddChunkRule
edits.
ContextDistributionInducer. Computes left and right context distributions for every token.
JensenShannonCategoryInducer. Clusters tokens whose context distributions are close under JensenShannon divergence or another symmetric distributional distance.
TwoPartMDLScorer. Computes an approximate L(G) + L(S | G) score.
GreedyAcceptancePolicy. Accepts strictly improving edits.
MemoryStore. Saves states in memory during a run.
JsonStore. Serializes grammars, categories, scores, and edit logs to disk.

12.1

MDL Components

A practical first approximation can use:

L(G) = Ltok (V ) + Lrule (R) + Lcat (C),
L(S | G) = Lparse (S, G) + Lresid (S, G).
Here V is the vocabulary, R is the set of productions, and C is the set of categories. The residual
term may initially be zero if the grammar must reproduce the observed corpus exactly. Later it
may encode exceptions, noisy emissions, or probabilistic alternatives.

13

Search Design

Search should be pluggable. Do not put too much search intelligence inside the pattern miners or
category inducers. A miner proposes; the search layer decides.
Useful search policies include:
Greedy search. Try all proposals and accept the best strict improvement.
Beam search. Keep the top B grammar states at each depth.
Annealing search. Sometimes accept worse edits to escape local optima.
Hyperon-guided search. Ask Atomspace/MeTTa for promising edits, edit sequences, or abstractions.
Evolutionary search. Mutate grammars and select by score.
The public API should allow these policies to be swapped without changing state objects, scorers,
or miners.

Migration Path Toward Hyperon

The migration path should be incremental:
v0.1. Pure Python symbolic strings. NGramPatternMiner reads Corpus directly.
v0.2. Add fact projection. Core states can be projected into a MemoryFactStore.
v0.3. Add HyperonFactStore. It round-trips the same facts as MemoryFactStore.
v0.4. Add HyperonPatternMiner. It implements PatternMiner and returns chunk proposals.

Practical Milestones

A sane implementation order is:
1. Domain core. Implement IDs, tokens, categories, productions, grammar states, edits, proposals, and scores.
2. Symbolic string MVP. Fit from list[str]. Add NGramPatternMiner, simple chunk rewriting, approximate MDL, and a greedy induction loop.
3. Categories. Add context-distribution computation, hard category induction, category-sensitive
rules, diagnostics, and token explanations.
4. Persistence and reproducibility. Add JSON grammar format, edit-log replay, deterministic random seeds, snapshot tests, and stable text renderings.
5. Continuous symbolic dynamics. Add delay embedding, grid partitioning, k-means partitioning, and a Symbolizer protocol.
19

6. Fact layer. Add Fact, FactStore, MemoryFactStore, and projection from grammar states
to facts.
7. Hyperon adapter. Add HyperonFactStore, atom/fact conversion, and round-trip tests.
8. Hyperon-native algorithms. Add HyperonPatternMiner, HyperonCategoryInducer, and
eventually HyperonGrammarSearcher.

19

Testing Invariants

The tests should enforce the theory, not just the current implementation.

19.1

Chunk Invariants

1. A chunk token must have exactly one production.
2. A production right-hand side must be non-empty.
3. Expanding a rewritten chunk must preserve the original corpus.
4. A production marked as useful must be used at least twice in the relevant corpus or grammar
representation.

19.2

Category Invariants

1. A category token must have at least two members.
2. A category is not a production.
3. Category expansion denotes alternatives, not concatenation.
4. In hard-category mode, a token belongs to at most one category at a given level.
5. In soft-category mode, membership weights are explicit and normalized under the chosen
convention.

19.3

MDL Invariants

1. Accepted greedy edits must not increase total description length.
2. model_bits + data_bits == total_bits up to numerical tolerance.
3. Removing unused rules should not worsen exact data reconstruction.
4. The same grammar and corpus should always receive the same score from a deterministic
scorer.

19.4

Reproducibility Invariants

1. Same seed plus same input yields the same grammar.
2. Edit-log replay reconstructs the identical state.
3. JSON serialization round-trips all grammar objects and scores.
20

19.5

Backend Invariants

1. MemoryFactStore and HyperonFactStore must round-trip the same fact set.
2. Backend-specific miners must return valid Proposal objects.
3. A backend may rank proposals differently, but it must not violate the core type invariants.

Risks and Antipatterns

21.1

Antipattern: Hyperon Everywhere from Day One

It is tempting to make every CLA object an Atomspace atom immediately. This risks coupling the
entire library to backend APIs before the CLA domain model is stable. It also makes early testing
and packaging harder. The safer path is to implement the domain model in pure Python and then
project it into a fact layer.

21.2

Antipattern: Miners Mutate State

A miner that directly changes the grammar makes search hard to reason about. Miners should
propose, not mutate. State changes should flow through EditApplier and be recorded in the edit
log.

21.3

Antipattern: Categories as Long Chunks

Encoding M = {A, D, F } as a production like M → ADF is wrong for CLA. The category M
denotes a set of possible fillers, not the sequence A then D then F .

21.4

Antipattern: Scoring Hidden in Search

If a pattern miner secretly uses one scoring objective while the global search uses another, debugging
becomes painful. Miners may estimate benefits, but accepted edits should be judged by the official
scorer.

22

Summary of the Architectural Move

The library should begin as:
pure Python grammar state
pure Python miners
pure Python MDL scorer
pure Python edit applier
fact projection added early
Hyperon adapter added later
Hyperon-native cognition added last
The essential abstraction is:
CLA core objects ↔ backend-neutral facts ↔ Hyperon atoms.
This provides a practical tool quickly while leaving a credible path to deeper Hyperon-native
intelligence: Atomspace-stored grammar graphs, MeTTa pattern mining over symbolic trajectories,
category induction by graph and inference algorithms, and metagraph rewrite search over candidate
grammars.
